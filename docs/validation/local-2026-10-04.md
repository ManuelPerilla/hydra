# Validación local — 4 de octubre de 2026

Entorno: Windows, Docker Desktop con engine Linux amd64, k3d 5.9.0 y k3s v1.35.5-k3s1. Un servidor y un agente Kubernetes son contenedores del mismo equipo. Los timestamps UTC del experimento corresponden al 5 de octubre; en America/Bogota todavía era el 4 de octubre.

## Aplicaciones

| Componente | Resultado |
| --- | --- |
| ASP.NET Core 10 | 13 pruebas aprobadas, ninguna omitida; PostgreSQL 17 real |
| Rust | 13 pruebas aprobadas; cargo fmt y clippy con warnings como errores |
| Next.js | 11 pruebas aprobadas; TypeScript y build de producción |
| Infraestructura | 20 pruebas aprobadas; Terraform local/home-tunnel/oracle y políticas Kubernetes |

Las pruebas API incluyen CSRF, idempotencia HTTP, cupo único ante lease vencido, claves Data Protection compartidas/cifradas, dos clientes SignalR conectados a APIs diferentes y OAuth con proveedor simulado, cookies Secure y redirect HTTPS.

Las pruebas Rust cubren precondiciones, ownership, recuperación atribuida al controlador original y comportamiento conservador ante pérdida de contexto. El adaptador X permanece desactivado.

Las pruebas frontend cubren traducciones, contratos API y replay/cursor. La revisión visual incluyó desktop y móvil de 375 px en árabe RTL sin desbordamiento.

Infraestructura: siete pruebas de políticas y trece de FinOps/arranque. El inventario OCI se probó con respuestas simuladas: cuotas compartidas, reconciliación por IDs Terraform, recursos no gestionados, state antiguo y backups. La prueba ejecutó el preámbulo real de shell con un fallo simulado del montaje y comprobó que se detiene; no formateó discos ni instaló k3s en el host. Se validaron recursos Oracle y un pod ACME mediante dry-run en un namespace restringido existente, sin crear recursos cloud.

Total: **57 pruebas automatizadas** entre aplicaciones e infraestructura, más **cinco escenarios nativos Terraform** que aprueban instalación/update y rechazan excesos de compute, almacenamiento y backups. Estos escenarios usan solo terraform_data, sin provider OCI. La revisión de navegador y el smoke Kubernetes se registran aparte.

## Experimento real

El smoke test local verificó:

1. Dry-run completado sin cambiar el UID del pod.
2. Dos POST con la misma clave devolvieron el mismo ID.
3. Borrado real del UID autorizado `6ba3617e-60b2-4ed5-a1e4-7f648da027ad`, experimento `4cdbe8b0-bd88-4d06-92a4-141b851257ad`.
4. Desaparición del UID original y vuelta a dos pods Ready del ReplicaSet verificado.
5. Recuperación observada de **2.142 ms**, medida por el agente en esa ejecución.

El navegador mostró SignalR en vivo, el resultado y los eventos reales. Una simulación adicional enviada desde la UI terminó correctamente. Se representa su duración con “—”, pues no hubo interrupción que medir.

[Captura verificada de la consola](assets/hydra-console.jpg).

La evidencia completa queda en `.local/smoke-results.json`, ignorada por Git. Puede reproducirse con:

```sh
python scripts/smoke.py
python scripts/smoke.py --inject
```

El segundo comando permite un borrado únicamente en el origen local predeterminado, sobre el laboratorio. No usar como prueba contra sistemas externos.

RBAC comprobado con el servidor: permite consultar ReplicaSets en `chaos-demo` y deniega eliminar pods de `hydra-system`. Todos los manifiestos locales pasaron dry-run del API server.

## Memoria observada

Una muestra de `kubectl top pods` después del experimento mostró **4 MiB de working set del agente**, API aproximadamente 42–102 MiB por pod, web 48 MiB por pod y PostgreSQL 52 MiB. Es una muestra puntual con poca carga, no un benchmark de RSS ni un límite garantizado.

Los límites configurados son API384Mi, web256Mi, agente96Mi y PostgreSQL512Mi. HPA limita API y laboratorio a tres pods; no crea VMs.

## Límites de esta validación

- Las tres imágenes se construyeron y ejecutaron en amd64. La API también produjo un artefacto OCI con variantes amd64/arm64.
- No existe emulación ARM funcional en este Docker Desktop. La ejecución ARM del stack completo corresponde al pipeline nativo configurado; no se ha ejecutado remotamente.
- Terraform init/validate no demuestra que haya capacidad A1 ni elegibilidad de una cuenta. No se aplicó infraestructura pública ni se consultó una cuenta OCI real.
- No se probó GitHub OAuth contra GitHub real, emisión/renovación ACME pública, failover del host ni restauración desde una copia independiente.
- No se ha certificado carga masiva de telemetría ni un SLO de recuperación.
- Los workflows y bots necesitan un repositorio público remoto; no se publicaron imágenes, posts ni tweets, ni se creó Discord.

Las rutas públicas requieren comprobar estos puntos antes de anunciar una release de producción.
